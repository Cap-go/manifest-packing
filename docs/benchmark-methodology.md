# Local Workers benchmark

Run `bun install`, `bunx wrangler types bench/worker-configuration.d.ts`, then `node bench/run.mjs suite`. The runner uses Node 22 or newer and the `ws` inspector client. The benchmark itself executes in Wrangler's local workerd runtime with `nodejs_compat`; it does not deploy, use remote bindings, or read customer data. Loopback ports default to 8787 and 9231 and can be changed with `BENCH_PORT` and `BENCH_INSPECTOR_PORT`.

Other runs: `node bench/run.mjs quick`, `node bench/run.mjs matrix`, `node bench/run.mjs memory`, and `node bench/run.mjs probe`. An optional second argument chooses the report path. Each report records runtime, Wrangler, Node, CPU, compatibility date, a SHA-256 of the immutable Worker bundle, raw timing samples, memory samples, and process RSS samples. Bun bundles the TypeScript benchmark into a fresh OS temporary directory before Wrangler starts; all measured code executes in workerd. This prevents source edits from hot-reloading a running measurement. Wrangler logs and ephemeral state also stay in that directory. Telemetry is disabled in the project and subprocess environment.

## Workloads and timing

The runner rejects occupied service/inspector ports before spawning. Startup has one 30-second deadline covering readiness, inspector discovery, WebSocket connection, and runtime initialization. Readiness attempts have a 1-second deadline, inspector discovery and handshake are capped at 5 seconds, and ordinary HTTP requests (including response bodies) at 120 seconds. Shutdown signals only the detached child process group created by this runner, then confirms child closure, group disappearance, and release of both ports. It allows 5 seconds for graceful termination and another 5 seconds after forced termination; a cleanup failure is reported rather than starting another case. Reports include a separate runner-source fingerprint for this lifecycle implementation.

All fixtures are deterministic synthetic data. Small, median, p95, and maximum are _scenario labels_, with 10, 1,000, 5,000, and 10,000 rows; these are not asserted production percentiles. Additional 10,000-row cases cover RSA v2 base64, RSA v3 hexadecimal, Unicode filenames, and long paths. Paths mix legacy, delta, and literal forms. Data is validated by hashing every decoded field against the sorted source tuples outside the timed loop.

Each suite timing case starts a new Wrangler/workerd process. It encodes the fixture first, then measures the first decode in the fresh isolate, three warmup decodes, and nine batches of repeated decode calls. Batches contain 100 iterations for the 10-row case, ten for 1,000 rows, and two for larger cases. The Worker yields for 5 ms outside each warmup/batch measurement so normal runtime scheduling and memory sampling can run; it never forces garbage collection. Memory and RSS monitors remain active during timing, so reported times include any inspector interruption overhead. First-decode time excludes startup, fixture generation, encoding, HTTP transport, and inspector connection; encoder use can warm shared helpers. This is not production cold-start latency. Batch duration divided by iterations includes allocation and normal garbage collection. The runtime clock has millisecond resolution, so the small and median cases have visible quantization. JSON.parse measurements use the same four-field tuples and include neither fetching nor validation; they are a baseline, not an equivalent integrity-checking protocol.

Matrix mode reuses the isolate and compares raw/prefix names, none/Brotli/Zstandard compression, and absolute/delta size encoding on identical rows. Every matrix case uses monotonic synthetic file sizes because delta mode requires monotonic sizes after filename sorting. Node creates all matrix packets, then sends them to the local Worker; the Worker independently regenerates the expected fixture and validates the decoded fields. Node encoding time is identified separately from Worker decoding time. First-decode matrix numbers are explicitly not cold. Suite timing and memory modes also test normal Worker packing with automatic compression.

### Native codec compatibility

The pinned workerd runtime's Zstandard compressor fails for valid high-entropy inputs at 65,536 bytes and above in our synthetic probe. This reproduces [workerd issue 6769](https://github.com/cloudflare/workerd/issues/6769); the [proposed upstream fix](https://github.com/cloudflare/workerd/pull/6773) remains open as of 2026-09-25. Changing `chunkSize`, compression parameters, or `info: true` did not resolve it. Automatic compression skips a failed optional candidate and keeps a successful Brotli/raw representation. Explicit Zstandard compression still reports a compression error on affected inputs. Native Zstandard decoding is measured using Node-produced packets; the matrix does not disguise Node encoding as successful Worker encoding. `probe.json` preserves the aggregate synthetic reproduction and native input-consumption checks.

## Memory measurement and limits

The monitor connects to the actual workerd inspector and requests CDP `Runtime.getHeapUsage`. It records `usedSize` (used JavaScript heap), `totalSize` (allocated JavaScript heap), `backingStorageSize` (ArrayBuffer/external-string backing), and `embedderHeapUsedSize` independently. Only when the latter fields are present does it also calculate their same-sample sum with used heap. Missing fields remain missing; they are never treated as zero. This sum is a diagnostic, not Cloudflare's authoritative total memory accounting, and can omit native codec workspace.

Sampling requests occur every 8 ms after the previous response. Actual elapsed timestamps expose scheduling and inspector delays. A separate measurement sets CDP breakpoints immediately after both blocks are decompressed and immediately before the decoded entries return, and records memory while the isolate is paused. The runner verifies that both distinct code locations were reached; these pauses never occur during timing runs. This captures the live decoded buffers and output at known allocation checkpoints, but not the peak inside a native codec call.

Each memory phase starts a fresh Worker and records its own fixture preparation baseline. Normal runs hold two decoded arrays alive, waiting 40 ms after each decode so samples can observe them, and test two unguarded concurrent requests holding output for 500 ms. The admitted workload sends eight concurrent requests; twenty sequential admitted requests each hold output for 1 ms. No phase forces garbage collection. Sampling can miss short transient allocations and may be delayed by synchronous execution. Measured maxima are lower bounds on true peaks, never proof of a 128 MB guarantee.

`node bench/run.mjs stress` intentionally increases unguarded retained copies and concurrent requests to eight. It can fail the hard memory check. The checked-in `stress-unsafe.json` records an actual failure: the long-path concurrent phase reached 137,647,208 accounted bytes. This result is not counted as a passing memory test. Retaining arbitrary outputs defeats a per-operation memory limit; callers must reserve space until outputs are consumed or evicted.

Separately, `ps` samples RSS for descendants of the runner's Wrangler child. Workerd-process RSS includes runtime/native allocations and possibly multiple isolates, while Wrangler/helper RSS belongs to host tooling. Neither is the isolate's memory usage. Do not subtract CDP heap from RSS and call the difference this decoder's native memory.

Cloudflare documents 128 MB per isolate shared across concurrent requests, including JavaScript and WebAssembly memory. The library's default `maxMemoryBytes = 96 MiB` is conservative per-operation accounting, not a measurement of all live application memory. A 96 MiB operation budget leaves only 32 MiB to a 128 MiB interpretation of the platform ceiling; because the platform documents MB, use additional margin rather than relying on that interpretation. Caller buffers, application state, retained previous outputs, codec native allocations, and unrelated requests still count.

The harness flags sampled accounting above 96 MiB and fails the run above a hard 128,000,000-byte accounting limit. That diagnostic is **not** an allocation interceptor and does not prevent an allocation between samples. The separate guarded concurrency example reserves 72 MiB before entering decode, passes that limit to the library, and rejects additional concurrent decodes with HTTP 429 while the reservation is held. It reserves 24 MiB for the application within a 96 MiB planning ceiling. The reservation is released only after consuming the decoded output. The runner requires exactly one successful request and seven rejected requests. This intentionally conservative one-at-a-time example demonstrates admission control; an application must measure its own baseline and keep reservations for any cached or otherwise retained output. Merely serializing synchronous decode calls is insufficient if results remain alive across awaits.

Production acceptance requires bounded upstream reads, the library's input/length/decompression guards, per-isolate admission and retained-output accounting, and measurements in the surrounding application with its real baseline. Local workerd success cannot promise the production runtime will never exceed its platform ceiling.
